# v1.6.0 验证记录：未满足严格留档

2026-11-23，本地 Mihomo Meta v1.19.34 Windows amd64（go1.26.11、with_gvisor）测试，12 项中 11 项稳态／边界检查通过，1 项严格留档失败。候选暂不部署。

使用仓库 `scripts/check_liangxinyun_priority.py`，节点、订阅、目标响应均为回环地址的合成 HTTP CONNECT 服务，无真实订阅或路由器参与。夹具将检测周期缩短为 1 秒、超时缩短为 300 ms；实际候选的 HTTPS 204 地址、60 秒周期与 5 秒超时没有按生产时序测试。

| 项目 | 结果 |
| --- | --- |
| 四档名称筛选、编号与分隔符、来源隔离、TikTok 组形状 | 通过 |
| 稳态类别优先于低档更低延迟 | 通过 |
| 同档只失去一个节点时严格留档 | **失败，实际流量提前进入下一档** |
| 三次整档失效，依次进入下一档 | 通过 |
| 高优先级恢复、档内更低延迟自动选择 | 通过 |
| 空档跳过、订阅新增编号 12 自动纳入 | 通过 |
| 四档全失效无成功出口、恢复自动选择 | 通过 |

第二轮复现中，日本专线 02 超时，日本专线 01 始终可用。控制器 API 显示专线 01 的 `alive: true`，新建 HTTP 请求却经日本高速 02 返回 200。采样在故障注入约 0.92 秒后看到日本高速，约 8.77 秒后回到日本专线。以上时间只适用于加速夹具，不代表路由器收敛时长。该脚本因此返回非零状态，不能将 12 项都称为通过。

上游 [Mihomo #2588](https://github.com/MetaCubeX/mihomo/issues/2588)、[#2612](https://github.com/MetaCubeX/mihomo/issues/2612)记录了同类现象，2026-11-23 查询仍为 Open。读取 Alpha `fallback.findAliveProxy` 仍只检查嵌套组自身的 `AliveForTestUrl`，不会聚合所有叶节点。调整间隔不能证明严格条件已满足；扁平 fallback 可绕开嵌套，但组内按固定顺序选择，不符合最低延迟要求。

用户随后选择保留严格顺序，授权准备独立自动控制器；后续实现见 [v1.7.0](../v1.7.0/REQUIREMENTS.md)。本版作为对照保留，未替换正式滚动模块、未部署路由器、未创建正式 Release。OpenClash 实际合并与目标 alpha 核心兼容性未在本轮验证。
